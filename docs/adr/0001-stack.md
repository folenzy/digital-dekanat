# ADR 0001. Стек и хостинг

Статус: принято (2026-11-07). Решение пользователя: подход A.

## Контекст
- Нужен рабочий прототип, который открывается из России без VPN до 28 ноября 2026.
- Бюджет минимальный: VPS около 200–300 ₽/мес, обычно 1 vCPU и 1 ГБ RAM.
- ТЗ требует гибкости масштабирования под разное число пользователей.
- Нужны уведомления в реальном времени.
- Срок отправки 25 ноября, первая версия как можно раньше.

## Рассмотренные варианты
1. **Next.js (App Router) + PostgreSQL, Docker Compose + Caddy.** Одно приложение на TypeScript, отдельная БД.
2. Отдельный API (NestJS/FastAPI) + SPA (React). Почти вдвое больше работы и больше поверхность атаки.
3. Next.js + SQLite. Легче всего, но несколько копий приложения не могут работать с одной базой.

Хостинг: Vercel, Netlify и Cloudflare отклонены из-за сообщений о блокировках и замедлении в РФ. Выбран российский VPS.

## Решение
Вариант 1. Дополнительно:
- Drizzle ORM, миграции в репозитории;
- собственная аутентификация: argon2id, сессии в БД, cookie `__Host-`;
- realtime через SSE, а между копиями приложения через PostgreSQL `LISTEN/NOTIFY`;
- образ собирается локально и переносится на VPS, на сервере только запуск.

## Последствия
- Чтобы масштабироваться, достаточно добавить копии `app` за Caddy: сессии, ограничение попыток и события уже живут в PostgreSQL. Копии стартуют одновременно без конфликтов: миграции и первичное заполнение идут под advisory-блокировкой (`src/server/boot.ts`).
- Проверено замером 15.11.2026 (`loadtest/README.md`): 1, 2 и 3 копии того же образа за Caddy — три копии дают в 2,5–2,7 раза больше страниц в секунду, ошибок нет, живые события между копиями доходят только адресату. Для прода при добавлении копий нужны две правки: в `deploy/Caddyfile` — распределение по всем копиям (`dynamic a app 3000`, как в `loadtest/Caddyfile`), в PostgreSQL — `max_connections` не меньше 11 на копию (пул 10 + `LISTEN`) плюс запас; сейчас 30.
- На 1 ГБ RAM нужны урезанные настройки PostgreSQL, ограничение памяти Node и swap на сервере.
