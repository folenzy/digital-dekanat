# «На связи» — цифровой деканат Университета Ориентир. Дизайн-документ

Дата: 2026-11-07. Статус: **одобрено пользователем** (после проверки субагентом-ревьюером).
Источник требований: ТЗ конкурса «Цифровой деканат будущего» и мастер-промпт `prompts/00-master-prompt.md`.
Пометка **[решение ИИ]** означает выбор, который сделал ассистент, а не пользователь; его можно оспорить.

---

## 1. Зачем это нужно

**Проблема (личный опыт автора, опрос однокурсников не проводился):**
- непонятно, куда писать, чтобы информация дошла до деканата;
- со стороны студента деканат «недосягаем»: трудно списаться;
- ответы приходят долго или не приходят вовсе.

Чаще всего автору нужно было писать в деканат по трём темам: **справки, учебные вопросы, стипендия**.

Плюс общая проблема из ТЗ: учебная жизнь разбросана по сайтам, системам, чатам и почте, а с телефона всё это неудобно.

**Главная идея кабинета:** «деканат, до которого можно достучаться».
1. Студент всегда знает, **куда** писать: одна кнопка, обращение само уходит в нужный отдел.
2. Студент видит, **кто** занимается его вопросом и **когда** ждать ответа: обещанный срок и таймлайн, как у посылки.
3. **Деканат пишет первым:** кабинет сам подсказывает, что студенту положено и что горит.
4. Ответ приходит **сразу**: уведомление в реальном времени, без перезагрузки.

Расписание и оценки сделаны хорошо и полностью, но в описании для жюри акцент на связи с деканатом.

## 2. Цели, не-цели, анти-цели

**Цели (волна 1, сделать как можно быстрее, чтобы отправить работу и потом доводить):**
- полное обязательное ядро ТЗ: вход и профиль, расписание, успеваемость, заявки и справки, уведомления;
- обращения в деканат с маршрутизацией по отделам, сроком ответа, таймлайном и перепиской;
- помощник «Спроси деканат»: поиск по базе ответов вымышленного вуза с передачей вопроса сотруднику;
- «Деканат пишет первым»: персональные подсказки по правилам;
- уведомления в реальном времени;
- кабинет сотрудника: очередь с таймерами, ответы, статусы, объявления;
- работа на телефоне от 360 px;
- безопасность с автотестами, вымышленные данные;
- файлы и инструкция для деплоя на российский VPS, **живой сайт уже в волне 1** (отправляем как можно раньше, дальше обновляем);
- журнал процесса для жюри.

**Волна 2 (после отправки первой версии, до 25 ноября):** справка в PDF с QR-проверкой подлинности; табло прозрачности деканата; запись на приём по слотам; калькулятор «какой балл нужен»; экспорт календаря (.ics); PWA, тёмная тема, офлайн-расписание; полировка дизайна и анимаций; видео; итоговое описание.

**Не-цели:**
- настоящая нейросеть в первой версии (пользователь выбрал «пока без неё»); оставляем точку расширения;
- интеграция с реальными системами любого вуза: никогда;
- загрузка файлов студентом в первой волне (лишняя поверхность атаки) **[решение ИИ]**;
- смена пароля для демо-аккаунтов: жюри пользуется общими аккаунтами, и смена пароля одним экспертом сломает вход остальным **[решение ИИ]**.

**Анти-цели (провал, даже если «технически работает»):**
- студент может увидеть чужие данные любым способом;
- кабинет выглядит как макет: кнопки никуда не ведут, данные не сохраняются;
- кабинет похож на официальный сервис реального вуза;
- шаблонный «AI-вид» интерфейса;
- перегруженность разделами в ущерб продуманности;
- в день проверки у жюри «сегодня» пустое, потому что демо-данные устарели.

## 3. Ограничения

- ТЗ: работающий прототип по ссылке; телефон от 360 px; только вымышленные данные; пометка «концепт для конкурса»; без логотипа вуза; лицензии стороннего; безопасность (только свои данные, пароли не в открытом виде, ключи не в коде и не в браузере); доступ из России без VPN до 28 ноября; минимум 2 студента и 1 сотрудник.
- Срок отправки: **25 ноября 2026**. Приём работ с 8 ноября 19:00 МСК. По ТЗ работу можно заменять до дедлайна, оценивается последняя версия; ссылка на сайт не меняется, поэтому сайт можно обновлять и после первой отправки.
- Масштабирование по ТЗ: стек «адекватный задаче и гибкий с точки зрения масштабирования под различное количество пользователей». Достаточно, чтобы архитектура позволяла масштабироваться и это было обосновано. В проде работает одна копия приложения; `docker compose up --scale app=N` и общий слой состояния в PostgreSQL описаны в ADR. Нагрузочный замер с цифрами для описания можно сделать во второй волне **[решение ИИ]**.
- Хостинг: дешёвый VPS российского провайдера (ориентир 200–300 ₽/мес, обычно 1 vCPU, 1 ГБ RAM). Vercel, Netlify и Cloudflare не используем. VPS арендует пользователь.
- Домен (решение пользователя): **пока без домена.** Временный бесплатный адрес вида `<IP>.sslip.io`. Возможность выпустить на него HTTPS-сертификат проверяем при деплое; если не получится, честно описываем ограничения и предлагаем домен. Caddy настраивается так, чтобы домен можно было подставить одной переменной.
- Окружение разработки: Windows 11, Node 24, npm, git, Docker. Python нет, поэтому Playwright используем для Node.
- Часовой пояс приложения: Europe/Moscow.

## 4. Подходы

| | Подход | Плюсы | Минусы |
|---|---|---|---|
| **A (выбран)** | Одно приложение Next.js (App Router) + PostgreSQL, Docker Compose + Caddy | Быстрее всего; один язык; база отдельно, приложение можно запустить в нескольких копиях | Сборка тяжела для 1 ГБ RAM, поэтому образ собираем локально и переносим |
| B | Отдельный API (NestJS/FastAPI) + SPA (React) | «Взрослая» архитектура | Почти вдвое больше работы и мест для ошибок безопасности; меньше времени на полировку |
| C | Next.js + SQLite | Самый лёгкий для VPS | Не масштабируется на несколько копий, это слабое место по требованию ТЗ |

**Выбор пользователя: A.** Причина: скорость, понятная история масштабирования, укладывается в дешёвый VPS.

## 5. Решённые вопросы «как»

**Пользователь решил:**
- хостинг: VPS в России;
- стек: подход A;
- помощник без внешней нейросети, поиск по базе ответов;
- визуальный стиль A «Бумага» (`docs/design/mockups/01-visual-style-options.html`); **13.11 заменён** системой «Ведомость» — см. §11 и `DESIGN.md`;
- название: кабинет **«На связи»**, подзаголовок «цифровой деканат»; вуз **«Университет Ориентир»** (вымышленный);
- в волну 1 входят «Деканат пишет первым» и уведомления в реальном времени, остальные вау-идеи во вторую волну;
- темы обращений: справки, учебные вопросы, стипендия.

**[решение ИИ]:**
- собственная аутентификация без внешних сервисов: argon2id, сессии в БД, защищённая cookie;
- ORM Drizzle; миграции в репозитории;
- realtime через Server-Sent Events, а между копиями приложения через PostgreSQL `LISTEN/NOTIFY` (масштабирование без Redis);
- поиск помощника: полнотекстовый поиск PostgreSQL с русской конфигурацией;
- «единое окно»: один деканат обслуживает все три факультета (это и есть концепт «понятно, куда писать»), внутри деканата три отдела-очереди;
- шрифты: тело **Golos Text** (кириллица проверена); заголовки — serif **с кириллицей**: Literata (основной кандидат), запасные Lora или PT Serif. Fraunces с макета **отклонён: нет кириллицы** (проверено по Google Fonts CSS 07.11). Финальный выбор на этапе `frontend-design`;
- иконки Lucide, лицензию сверить по LICENSE пакета (в мастер-промпте указан MIT; по памяти ассистента это ISC — проверить).

## 7. Навигация и экраны

Мобильная навигация: нижняя панель из пяти вкладок **Сегодня · Пары · Учёба · Деканат · Профиль**, плюс колокольчик уведомлений со счётчиком в шапке. На десктопе (≥ 1024 px) та же структура слева, контент по центру, справа колонка «Сегодня/уведомления» там, где уместно. Пометка «Концепт для конкурса · не официальный сервис» видна на каждом экране и на странице входа.

### 7.1 Вход
- Логин и пароль. Ошибка одна для неверного логина и неверного пароля: «Неверный логин или пароль».
- Ограничение попыток: по паре «логин + IP» и отдельно по IP, понятное сообщение «Слишком много попыток, попробуй через N минут». Блокировки только по логину нет: аккаунты демо общие и опубликованы, поэтому такая блокировка не защищает, зато позволяет любому закрыть вход всему жюри **[решение ИИ]**.
- Состояния: загрузка на кнопке, ошибка сети, сессия истекла (редирект на вход с пояснением).
- Тестовых учёток на странице входа нет, они в README и в комментарии к работе **[решение ИИ]**.

### 7.2 Сегодня (главный экран)
Приветствие, дата, дальше блоки по важности:
1. **«Деканат пишет первым»:** 0–3 персональные карточки с действием (см. 7.8).
2. **Пары сегодня:** ближайшая или идущая сейчас пара; изменения видны сразу (старая аудитория зачёркнута → новая). Выходной или пар нет — «Сегодня пар нет», и следующая пара.
3. **Мои обращения:** активные, со статусом и сроком ответа.
4. **Скоро дедлайны:** контрольные точки, сроки заявлений.
5. **Последнее объявление деканата.**

### 7.3 Пары (расписание)
- Переключатель «День / Неделя», полоса дней недели, переход между неделями, чётность недели.
- Карточка пары: время, номер пары, дисциплина, тип (лекция/практика/лабораторная), аудитория и корпус, преподаватель.
- Изменения: бейдж «Перенос», «Замена преподавателя», «Новая аудитория», «Отменена» (зачёркнуто), было → стало, комментарий.
- Подсветка идущей пары.
- Модель: недельный шаблон по чётности + изменения на конкретные даты (как в реальных вузах).

### 7.4 Учёба (успеваемость)
- Вверху сводка **«Как у меня дела»**: вердикт человеческим языком («Всё идёт хорошо» / «Есть риски» / «Есть долги»), средний балл, число долгов, допуски к сессии.
- Текущий семестр: дисциплины с формой контроля (экзамен, зачёт, дифференцированный зачёт), баллы по балльно-рейтинговой системе 0–100, разбивка по контрольным точкам, статус допуска.
- Вкладка «Сессия»: даты экзаменов и зачётов, аудитории, результаты.
- Вкладка «Зачётка»: оценки прошлых семестров.

### 7.5 Деканат (обращения, справки, заявления)
Объединяет «Заявки и справки» из ТЗ и связь с деканатом. Одна сущность **«Обращение»** с видом: вопрос, справка, заявление.

- **«Спроси деканат»** вверху: поле вопроса → помощник ищет по базе ответов (около 25 статей вымышленного вуза) → показывает ответ и ссылку «Оформить» на нужный тип обращения. Кнопка «Не помогло — написать сотруднику» создаёт обращение с уже заполненными темой и текстом.
- **«Новое обращение»**: шаг 1 — тема (Справки / Учебные вопросы / Стипендия); шаг 2 — подтип с пояснением, что понадобится и какой срок; шаг 3 — короткая форма под подтип. Перед отправкой показывается: «Уйдёт в: <отдел> · обычно отвечаем за <срок>».
- Подтипы:
  - Справки: об обучении; для военкомата; для соцзащиты; об обучении для стипендии/пособия; архивная (выписка оценок).
  - Учебные вопросы: пересдача; индивидуальный график; перевод; академический отпуск; другой вопрос.
  - Стипендия: повышенная академическая; социальная; материальная помощь; вопрос по выплате.
- **Мои обращения**: список с фильтром (активные / завершённые), статус, срок ответа.
- **Карточка обращения**: таймлайн статусов (Отправлено → Принято в работу (кем) → Нужно уточнение → Готово / Отклонено с причиной → Закрыто), обещанный срок с обратным отсчётом, переписка студент ↔ сотрудник внутри обращения. Для справки в статусе «Готово» — где и до какого числа забрать.
- Срок ответа (SLA) задаётся у подтипа в рабочих часах/днях; просрочка видна и студенту, и сотруднику.

### 7.6 Уведомления и объявления
- Колокольчик со счётчиком непрочитанных; страница уведомлений: все / непрочитанные, «прочитать всё».
- Типы: смена статуса обращения, новое сообщение от деканата, изменение в расписании, напоминание о дедлайне, объявление.
- Объявления деканата: лента с аудиторией (все / факультет / курс / группа), важные закреплены.
- **В реальном времени:** когда сотрудник отвечает или меняет статус, у студента без перезагрузки появляются тост и счётчик, а открытые экраны обновляются.

### 7.7 Профиль
ФИО, инициалы-аватар, факультет, направление и профиль, курс, группа, форма и основа обучения, номер студенческого (вымышленный), email (вымышленный), куратор группы. Кнопка «Выйти». Ссылка «О проекте»: концепт для конкурса, тестовые данные, как устроена защита.

### 7.8 «Деканат пишет первым» (правила)
Карточки вычисляются на сервере из данных студента, без нейросети. Набор правил волны 1:
- **Повышенная стипендия:** прошлая сессия без троек и долгов, средний ≥ 4,5, окно приёма открыто, заявление ещё не подано → «Ты проходишь на повышенную стипендию… Подать в 1 тап» (создаёт черновик заявления).
- **Риск недопуска:** до сессии меньше N дней, не сдана обязательная контрольная точка → «Для допуска по <дисциплине> не хватает <точки>, срок <дата>».
- **Долг:** есть академическая задолженность → «Пересдача по <дисциплине> <дата>. Записаться / задать вопрос».
- **Справка готова:** → «Справка готова, забери в каб. 214 до <дата>».
- **Деканат ждёт уточнение:** → «Ответь на вопрос по обращению №…».
- **Изменение в расписании сегодня/завтра:** → короткая карточка.

Карточка исчезает, когда условие перестало выполняться (например, заявление подано). Ручного «скрыть» нет, потому что аккаунты общие для жюри **[решение ИИ]**.

### 7.9 Кабинет сотрудника
- **Очередь:** вкладки Новые / В работе / Ждут студента / Закрытые; фильтр по отделу; сортировка по сроку; просроченные подсвечены красным; таймер «осталось 3 ч».
- **Карточка обращения:** минимум данных о студенте; «Взять в работу», ответить, запросить уточнение, «Готово» (для справки: где забрать), «Отклонить» с причиной. Все действия попадают в таймлайн.
- **Объявления:** создать, выбрать аудиторию, отметить важным, опубликовать → студенты получают уведомление в реальном времени.
- **Сводка:** новых, в работе, просрочено, среднее время первого ответа за неделю (основа для табло прозрачности во второй волне).
- Студент не может открыть ни одну страницу и ни один эндпоинт сотрудника.

## 8. Данные (логическая модель)

- `users`: id (uuid), login (уникальный), password_hash, role (student | staff), is_demo, created_at.
- `sessions`: id, token_hash (sha-256 от случайных 32 байт), user_id, expires_at, created_at, last_seen_at, user_agent.
- `login_attempts`: ключ (логин или IP), время, успех; для ограничения попыток, хранится в БД, чтобы работало на нескольких копиях.
- `faculties`, `programs` (направления), `groups` (факультет, программа, курс, название).
- `students`: user_id, ФИО, group_id, форма и основа обучения, номер студенческого, email, куратор.
- `staff`: user_id, ФИО, должность; `departments` (Справки и документы, Учебный отдел, Стипендиальный отдел); `staff_departments`.
- `teachers`, `disciplines`, `rooms`.
- `schedule_slots`: группа, день недели, чётность, номер пары, время, дисциплина, тип, аудитория, преподаватель.
- `schedule_changes`: группа, дата, номер пары, вид (перенос / отмена / замена преподавателя / новая аудитория / доп. занятие), новые значения, комментарий.
- `enrollments`: студент, дисциплина, семестр, форма контроля, баллы, итоговая оценка, допуск.
- `checkpoints`: enrollment, название, максимум, балл, срок, обязательная ли.
- `exams`: группа, дисциплина, тип, дата и время, аудитория; пересдачи.
- `appeal_types`: тема, подтип, отдел, SLA, описание, поля формы.
- `appeals`: id (uuid), номер для людей, student_id, type_id, department_id, assignee_id, status, данные формы (jsonb), sla_due_at, created_at, updated_at, closed_at.
- `appeal_events`: таймлайн (кто, что, когда); `appeal_messages`: переписка.
- `notifications`: user_id, тип, заголовок, текст, ссылка, read_at.
- `announcements`: автор, заголовок, текст, аудитория (факультет / курс / группа, всё nullable), важное, published_at.
- `kb_articles`: тема, вопрос, ответ, ключевые слова, связанный тип обращения, tsvector для поиска.

## 9. Безопасность

- **Доступ к данным только через серверный слой.** Каждая функция получает пользователя из сессии; владелец проверяется в самом запросе (`WHERE student_id = <из сессии>`). id из URL используется только как ключ поиска внутри своих данных; чужое → 404 (не раскрываем существование).
- Роли проверяются на сервере в каждом действии сотрудника; страницы сотрудника под отдельным префиксом с проверкой в layout и в каждом действии.
- **Автотесты (TDD):** студент A не получает профиль, оценки, расписание, обращения, сообщения, уведомления студента B ни по прямому URL, ни подстановкой id в API и серверные действия; студент не вызывает ни одно действие сотрудника; без сессии всё закрыто; поток событий отдаёт только свои события.
- Пароли: argon2id. Сессии: случайный токен, в БД только хеш; cookie `__Host-`, httpOnly, Secure (в проде), SameSite=Lax; срок жизни и выход с удалением сессии.
- CSRF: проверка Origin для мутирующих запросов (у серверных действий Next.js она встроенная) + SameSite.
- Ограничение попыток входа (логин + IP и IP); одинаковый ответ и сопоставимое время ответа для неверного логина и пароля.
- Защита от порчи демо: лимиты длины текстов, ограничение частоты обращений, сообщений и объявлений на пользователя **[решение ИИ]**.
- Валидация всех входных данных на сервере (zod); параметризованные запросы через ORM; экранирование вывода (React) и никакого `dangerouslySetInnerHTML` для пользовательского текста.
- Заголовки: CSP (с nonce), HSTS, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, frame-ancestors none. Без `x-powered-by`.
- Секреты только в env на сервере; `.env.example` в git; в браузер не попадает ничего, кроме публичных значений.
- Логи без паролей и токенов. Страницы ошибок без стектрейсов.
- Перед деплоем `security-review`, результат прикладываем к описанию.

## 10. Демо-данные, которые не устаревают

Жюри проверяет в разные дни до 28 ноября, поэтому «сегодня» не должно быть пустым.
- Расписание = недельный шаблон, поэтому пары есть в любую учебную неделю.
- **Ночной сброс демо (решение пользователя):** каждую ночь в 04:00 МСК задача по расписанию в контейнере возвращает базу к исходному состоянию. Все даты сценариев пересчитываются от «сегодня»: изменения в расписании на сегодня и завтра, обращение в работе со сроком в будущем, справка готова, дедлайны через несколько дней, свежие объявления. Днём всё, что сделали эксперты, сохраняется. В README и на странице «О проекте» написано: «Демо-данные возвращаются к исходному состоянию каждую ночь в 04:00 МСК». Сброс заодно откатывает возможную порчу демо (например, объявления от посторонних).
- Значит, сид — это функция «собрать демо-мир относительно даты X», а не статичный дамп. Сброс идёт в одной транзакции; сессии пользователей при сбросе удаляются.
- Окна приёма заявлений (например, на повышенную стипендию) считаются относительно «сегодня» и всегда открыты на ближайшие дни.
- Сессия: экзамены во второй половине декабря 2026.
- Тот же сброс можно запустить вручную командой.
- Все ФИО, номера и email выдуманы; номера студенческих в явно вымышленном формате.

## 12. Деплой

- Docker Compose: `app` (Next.js standalone), `db` (PostgreSQL с урезанными настройками памяти), `caddy` (HTTPS, сжатие), задача ежедневного обновления демо.
- Образ собирается локально (Docker уже установлен) и переносится на VPS (`docker save` → `ssh` → `docker load`); на сервере только запуск.
- Миграции применяются при старте; сид — отдельной командой и только на пустую базу.
- Бэкап: `pg_dump` по расписанию в папку на сервере.
- `docs/DEPLOY.md` — пошагово для новичка: аренда VPS, SSH, Docker, swap, запуск, HTTPS, обновление, проверка, перезапуск, бэкап.
- Ассистент не заходит на сервер и не деплоит без разрешения пользователя.

## 13. Проверка

- Vitest с реальной PostgreSQL (контейнер): серверный слой, правила «Деканат пишет первым», SLA, авторизация и IDOR.
- Playwright (Node): сквозной сценарий «вход → сегодня → расписание → оценки → новое обращение → сотрудник отвечает → студент получает уведомление в реальном времени» на 360 px и 1280 px; консоль без ошибок; скриншоты в `docs/screenshots/`.
- Проверка доступности (axe) на ключевых экранах.
