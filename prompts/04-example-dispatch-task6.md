## Решения контроллера для задачи 6 (из журнала)

Контроллер заранее закрывает места, где исполнителю пришлось бы угадывать, и **переносит уроки прошлых задач**:

1. Ошибки — объединение `Result<T>` (`{ ok: true, value } | { ok: false, error }`), а не исключения: страницы и формы показывают понятный текст.
2. UUID обращения проверяется до запроса к БД: мусорный id → `not_found`, а не исключение Postgres.
3. Частотные лимиты — сразу «зарезервировать, потом считать». **Урок задачи 4:** там ревьюер нашёл гонку, когда 20 параллельных запросов проходили лимит «5 попыток».
4. Ответ сотрудника на обращение в статусе «Отправлено» автоматически берёт его в работу.
5. Действовать может любой сотрудник отдела, а не только исполнитель (в демо все эксперты делят один аккаунт).
6. Для справки «Готово» требует место и срок выдачи.

Плюс решения из предварительной проверки плана, которые касаются задачи 6: `APPEAL_TYPES` (с zod-схемами полей) уже создан в задаче 3; `publish(userIds, event)` через `pg_notify` создаётся здесь же, а задача 9 добавит подписку и SSE; тест лимита «11 обращений в час» должен менять поля каждого обращения, иначе их склеит защита от двойной отправки (10 с).
